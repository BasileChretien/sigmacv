# Dependency hygiene (`allowScripts`, `overrides`)

> Maintainer reference, moved out of the root `CLAUDE.md` (which keeps the rules as one-liners): what keeps dependencies current, what it leaves to a person, and why.

**What actually keeps dependencies current** (audited 2026-09-02 — everything below is wired up, don't assume a gap without re-checking):

- **Dependabot version updates**, weekly, over four ecosystems: `npm`, `github-actions`, `docker` (Dockerfile only) and `docker-compose` (the compose stack). `docker` and `docker-compose` are **separate ecosystems** — the first does not scan compose files, which is how Caddy/Postgres/ClickHouse/Plausible/Metabase went unwatched until 2026-09-02.
- **Dependabot alerts + security updates**, enabled 2026-09-02. They were off before that, which is why eight high-severity advisories accumulated silently.
- **`.github/workflows/audit.yml`** — `npm audit --audit-level=high`, weekly and on any PR touching the manifests. Deliberately kept out of `ci.yml`: an upstream disclosure would otherwise redden every unrelated PR.
- **Patch and minor npm and GitHub Actions PRs merge themselves** (since 2026-11-04, after five Dependabot security PRs sat unmerged for two weeks while production ran a Next.js with a known denial of service). `.github/workflows/dependabot-auto-merge.yml` arms GitHub's auto-merge (squash) when `autoMergeDecision` in `scripts/dependabot-automerge.mjs` says so, and GitHub merges once the two required checks pass. Majors, Docker and Compose images, and `playwright` stay manual; both npm groups exclude the playwright pair, so it arrives alone and holds no other update back. npm security fixes come as ONE grouped PR (`groups.security`, `applies-to: security-updates`), so they are no longer red on each other's advisories. `dependabot-train.yml` (hourly) updates the oldest armed PR left behind main and dispatches `ci.yml` and `e2e.yml` on it: main requires up-to-date branches, Dependabot rebases only on a conflict, and a push made with the workflow token starts no workflow. Merges made by auto-merge start no `push` workflow on main either.
- **The server deploys main by itself.** `scripts/auto-deploy.sh`, in root's crontab every 15 minutes, runs `deploy.sh` with `DEPLOY_SHA` when main moves, checks `/api/health` from outside and emails the result (`DEPLOY_NOTIFY_EMAIL`, else `OPENALEX_MAILTO`). It deploys nothing, and emails once per commit, for a postgres, clickhouse or plausible image change (or an image given by a variable), a checkout that is not a fast-forward or has local changes, or a commit whose deploy already failed or ran past an hour. Pause it with `touch .deploy-state/paused`. Install, logs and rollback: `docs/SERVER-RUNBOOK.md` §10.
- Two exclusions in the `docker` ecosystem, both because the value is pinned to something else rather than free-floating: the **Playwright runtime image** (its tag is bound to the exact `playwright` npm version by `tests/dockerfile-playwright-sync.test.ts`, so it moves from the npm side) and the **builder's Node major** (pinned to the Node the Playwright runtime image ships — v24.18.1 as of 2026-09-02 — so it moves when that image does). Minor/patch still flow for both.
- Two exclusions in the `docker-compose` ecosystem, for images that are **not ours to bump**: **`postgres` majors** (the app DB, `plausible_db` and `metabase_db` share the tag and all hold live v16 data — a major is a dump/restore migration, and because deploy runs a bare `up -d` a merged major takes all three down on the next deploy) and **`clickhouse/clickhouse-server` outright** (Plausible CE pins the pairing: v3.2.1's own compose ships `24.12-alpine`, so it moves only when Plausible does). Postgres patches still arrive via the floating `16-alpine` tag on pull.
- **Image bumps are not covered by CI.** No workflow builds the Dockerfile or the compose stack, so a `docker`/`docker-compose` PR's green checks say nothing about it; the first thing to exercise one is `scripts/deploy.sh` on production. Read those diffs properly.

Two things automation still does **not** do: it merges no major and no image bump (deliberate — e.g. a Node major in the builder can silently desync from the Playwright runner's Node), and it deploys no change to a postgres, clickhouse or plausible image. Otherwise **merging is deploying**: what lands on main is live within about 15 minutes, so a change that needs a server-side step first (a new `.env` value, a data import) takes that step before the merge, or pauses the auto-deployer until it is done. Note what deploy.sh does once run: it calls a bare `docker compose up -d`, with no service filter, so Compose recreates **every** service whose image changed — not just `app`. A merged compose image bump therefore lands on the next deploy without further action, which is why a `postgres`/`clickhouse-server` major must never be merged casually: the next deploy would recreate it against a data directory the new major refuses to open. (The Caddyfile is the opposite case — bind-mounted, so no config hash changes and `up -d` does not recreate caddy; deploy.sh validates and reloads it explicitly. Image tags and mounted files behave differently.)

Two things need a human hand when dependencies change:

- **`allowScripts` in `package.json`.** From **npm 12** dependency install scripts are blocked unless the package is listed there; npm ≤ 11 ignores the field. Today it approves `esbuild`, `prisma` and `@prisma/engines` — the three that genuinely need to run (query engine download, esbuild binary). Entries are deliberately **name-only, not version-pinned**, so routine Dependabot bumps don't silently skip those scripts. When an install ends with "packages had install scripts blocked", review the package and then `npm install-scripts approve <pkg> --no-allow-scripts-pin` — don't blanket-approve with `--all`. The Dockerfile's global `prisma` install passes the equivalent `--allow-scripts=prisma,@prisma/engines` flag, since a global install has no `package.json` to read.
- **`overrides`.** These pin transitive dependencies forward past advisories their parent hasn't picked up yet (currently `postcss`, `nodemailer`, `@hono/node-server`, plus `mysql2`, `deepmerge-ts` and `fast-uri` inside the Prisma CLI). `npm audit` is expected to report **0 vulnerabilities**; if an override becomes redundant after the parent catches up, drop it rather than letting it drift.

Note that `npm audit` covers the repo tree only. The production image installs the Prisma CLI globally (`npm install -g prisma@7`), so the `mysql2` / `deepmerge-ts` / `fast-uri` overrides do **not** apply there — accepted, because neither is on a code path SigmaCV executes (Postgres only).
